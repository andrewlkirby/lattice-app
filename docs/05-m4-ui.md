# Sub-plan M4: User Interface

Parent: `00-preliminary-plan.md`, milestone M4 (component #7).
Depends on: M2 (model, commands, clip-state feed, serialization) and M3 (devices, `ParameterSpec`/parameter groups, racks, returns, sidechain).

## Goal
Replace the debug UI with a complete Live-style interface:
- a control bar
- the Session view with its mixer
- a Clip view with a piano roll that understands Colundi
- a Device view with custom device panels
- a browser with a searchable library
- tuning tools
- preferences, file handling, and MIDI/key mapping

**Priorities (from the preliminary plan):**
- **Quality and performance:** smooth, display-rate rendering at any zoom level, and no effect on audio.
- **No hard-coded sizes:** everything scales, and every panel can be resized or collapsed.
- **No hardware needed:** every action is a command that you can reach from a menu, a shortcut, or the mouse.

We copy Live's workflows and layout ideas, not its artwork. Every icon, color, and asset is our own.

**Out of scope here:**
- arrangement view (post-MVP; the main area keeps a tab slot for it)
- audio clip editing
- automation lanes
- note probability and velocity ranges (they need engine work; post-MVP)
- the controllers' own UIs (Virtual Push is M5)

### Found in the M3 hands-on checks
These are requirements for the new UI:
1. **Arm, sends and the mixer must never be scrolled out of view.**
   - In the debug UI, the mixer strips sit under the clip grid in one scrolling area. With a few scenes, the arm button and the send knobs disappeared below the window.
   - The Session view's mixer section (4b) is pinned at the bottom of the main area, outside the grid's vertical scroll. It still scrolls sideways with the tracks.
   - Arm is also in the track header.
2. **Arm follows the selection** (Live's "auto-arm"), as an option that's on by default.
   - Selecting a MIDI track arms it when no other track is armed by hand.
   - The computer keyboard and the on-screen keyboard then play what's selected.
   - In the checks, the keyboard silently played the previously armed Drum Rack.
3. **Sends show their level.**
   - Each send has a value readout (−inf … 0 dB) and the return's name.
   - Hovering a return strip highlights the sends that feed it.
4. **Inserting goes where you're looking.**
   - Double-click or Enter in the browser inserts into the chain shown in the Device view, including the selected chain inside a rack. In the debug UI it always went to the track's top-level chain.
   - Inserting an instrument where there already is one asks whether to replace it, or hot-swaps when hot-swap mode is on. It never replaces one silently.
5. **The computer keyboard follows a Drum Rack.**
   - Selecting a Drum Rack track moves the keyboard's range to the rack's visible pad page, so A plays the first pad on show.
   - In the checks, the range had to be moved by hand (Z twice) to reach note 36.
6. **The Sampler's root frequency is easy to see.**
   - It shows next to the waveform, as Hz plus the matching 12-TET note.
   - It is read from the file's root-note metadata (the WAV `smpl` chunk, AIFF `INST`) when there is one.
   - In the checks, a 440 Hz sample played at the default root of 261.63 Hz and needed the field typed by hand. Pitch detection stays out of scope (M3).
7. **Effects on returns default to fully wet.** A Reverb, Delay or Chorus inserted on a return track starts at 100% Dry/Wet. In the checks it started at 30%, which is right for a track but not a return.
8. **Editing while the set plays must reach the engine.**
   - The checks found a sidechain source chosen while playing that did nothing until the set was reloaded (fixed in M3, f4d5473).
   - M4's view-logic tests run their edits against a rendering engine, not only against the model (Tests, item 12).

### Order of work
- **The new UI is built beside the debug UI**, in `src/ui/`.
  - From 4a, the main window opens the new shell, and a "Debug UI" tab keeps the old views reachable.
  - Each feature's debug view is deleted once its new view covers it.
  - 4h deletes what's left.
  - This keeps every feature usable throughout, with no hardware, as the rules require.
- **Phases:** 4a → 4b → 4c → 4d → 4e → 4f → 4g → 4h.
  - 4c (Clip view) and 4d (Device view) only depend on 4a, so they can swap places.
  - 4e's library index runs on the 4a job pool.
  - Group tracks (4b) are the one engine change. They go first in 4b, with their own engine tests, before any UI is built on them.
- **Each phase** ends with:
  - its tests passing on Windows and Linux;
  - the frame-time targets checked for the views it adds;
  - a short hands-on check by the user, as at the end of each milestone, so problems like those above are found while the code is fresh.
- **First steps of 4a:**
  1. theme tokens and the widget library, starting with knob, NumberBox, fader with meter, and toggle;
  2. `CommandRegistry`, with every existing debug-UI action registered as a command;
  3. `EngineStateFeed` on `VBlankAttachment`, replacing the debug UI's timers;
  4. the background job pool;
  5. the window shell (control bar, browser slot, main area, detail view, info view, status bar), with the Debug UI tab inside it;
  6. frame-time measurement, so every later phase is measured from its first commit.

## Architecture — `src/ui/`

### Rules
1. **The UI never touches the engine directly.**
   - It edits the model (ValueTree + `UndoManager`) through typed wrappers.
   - It sends transport and launch actions as **commands**.
   - It reads live state (clip states, playheads, meters, spectrum frames, gain reduction) from one **`EngineStateFeed`**.
2. **One central command system** (`juce::ApplicationCommandManager` plus our own `CommandRegistry`):
   - Every user action is a command with an ID, a name, a category, and a shortcut you can change.
   - Menus, shortcuts, context menus, Key Map mode, and later Virtual Push and the hardware controllers all call the same commands.
   - This is how the no-hardware rule is enforced: a test checks that every engine and model action has a command.
3. **One refresh tick:** the `EngineStateFeed` is polled once per display refresh through `juce::VBlankAttachment` and passes changes to subscribed components. There are no per-component timers, and only the parts that changed are repainted.
4. **All file and disk work runs off the UI thread**, on a background job pool. This covers loading samples, indexing the library, building waveform peaks, and saving. The UI shows progress and never freezes.

### Rendering and performance
- **Windows:** JUCE 8's **Direct2D** renderer (hardware-accelerated).
- **Linux:** JUCE draws in software on Linux, so the heavy views (piano roll, waveforms, the spectrum analyzer, the session grid) are drawn with **OpenGL** (`juce::OpenGLContext`). The frame-time targets are measured on Linux too, and enforced once a real Linux machine is available.
  - The app runs on X11, and on **Wayland through XWayland**. Fractional scaling there may look soft; integer scaling looks sharp.
- **macOS:** JUCE's default CoreGraphics renderer.
- **Expensive views draw into cached images and only redraw what changes:** the piano-roll note layer, waveforms, the EQ curve, and the background grid.
- Waveforms use **peak data at several zoom levels**, built in the background when a sample loads and cached on disk.
- Meters, playheads, and clip progress are drawn in light layers on top, so they never repaint whole views.
- **Targets on the reference machine:**
  - A UI frame takes 8 ms or less with a 32×16 visible Session grid, all meters moving, and the piano roll showing 10,000 notes.
  - Startup and set loading meet the **performance charter** (`09-performance-charter.md` §1): window in ≤ 0.5 s, ready to use in ≤ 1.5 s, reference set playable in ≤ 3 s. Each click or key press shows a response within ≤ 1 frame, and idle CPU stays under 1%.
  - **No audio dropouts caused by UI activity:** a stress test checks this (see Tests).
- The UI thread runs at normal priority. The audio and worker threads from M3 are never blocked by it.

### Theme and scaling
- **Theme tokens:** every color, font size, spacing, and corner radius comes from a **theme token set**. Nothing is hard-coded inside components.
- **Themes included:**
  - a dark default, in the spirit of Live but with our own colors
  - a light theme
  - a high-contrast theme
  - users can make their own themes (JSON)
- **Zoom:** UI zoom runs from 50% to 250% and follows the system DPI on each monitor. All drawing is vector-based; the icons are our own SVGs.
- **Layout:** every panel can be resized, collapsed, and toggled (browser, detail view, info view, mixer sections). The layout is saved in two places:
  - globally, for the window and panels
  - per set, for the scroll and zoom position in each view

### Widget library — `src/ui/widgets/`
- **Knob** (and a bipolar knob), **slider**, and a **fader with a meter**.
- **NumberBox:** Live-style. Drag up or down to change it, double-click to type a value, and use modifier keys for fine adjustment.
- **Toggle buttons**, a **color palette picker**, and a **clip slot cell**.
- **Track header**, **meter** (peak and RMS, with peak hold), and **scrollbars and zoom bars**.
- **Common behavior for every widget:**
  - It is bound to a model property or a `ParameterSpec`.
  - It supports undo, shows a value tooltip, and resets to default on double-click or Delete.
  - It shows MIDI/Key Map overlays.
  - It registers in the **control registry** while it's on screen or could be brought on screen:
    - what it controls (a parameter ID and device, or a model property);
    - its name, group and owner (track, device, rack chain);
    - how to reveal it: select the track, open the device, expand it, open the rack chain, scroll.
  - MIDI Map, Key Map and Find (4g) all use the registry.
  - It works with the keyboard and supports screen readers (JUCE `AccessibilityHandler`).

- The theme system, the widget library and its control registry, `CommandRegistry`, `EngineStateFeed`, and the background job pool.

  - the computer keyboard toggle, with its range and velocity

- **Info view:** the hovered control's name, a short description, and its shortcut, as in Live. The text comes from the `ParameterSpec` and the `CommandRegistry`.
- **As built (2026-10-19):**
  - **Theme** (`src/ui/theme/`):
    - Every colour and size is a named token (X-macros in `Theme.h`; the names are also the JSON keys).
    - There are three built-in themes: Dark, Light and High Contrast.
    - A user theme in JSON names a base theme; any token it leaves out comes from the base, and every mistake is reported.
    - Widgets draw from the theme of their look and feel (`themeOf()`), so the snapshot tests can draw one widget in every theme.
    - A test checks WCAG contrast for text, dim and disabled text, accent text and the focus ring. It caught two weak Light colours, which were then fixed.
    - Zoom (50–250%) and the theme picker in Preferences come with 4g. Until then, View commands switch themes.
  - **Widgets** (`src/ui/widgets/`):
    - Knob, NumberBox, Fader with Meter, and Toggle, each bound through `ValueBinding` to a device parameter or a model property described by a `ParameterSpec`.
    - `ParameterSpec::normalisableRange()` is now the one range that devices, widgets and (later) controllers all turn a parameter through.
    - **Undo:** a drag is one undo step, and so is a burst of wheel or arrow-key steps.
    - **Mouse and keys:** drags are relative, with Shift for fine changes; double-click or Delete resets; Enter types a value in place. Letters pass through to the computer keyboard.
    - **Deviation:** a NumberBox types a value on double-click instead of resetting, as Live's number boxes do; Delete resets it.
    - Clicked toggles and command buttons don't take the keyboard focus, so Space stays Play/Stop.
    - Screen readers see each control's name, range and formatted value.
  - **Control registry:** bound widgets register with the registry of the window they're in (`ControlRegistry::Provider`, the shell) and leave it when they go. How to reveal a hidden control is added by each view as it's built (4b, 4d).
  - **Commands** (`src/ui/commands/`):
    - `CommandRegistry` sits on JUCE's `ApplicationCommandManager`, so menus and key mappings work as JUCE's do.
    - Shortcuts are saved by stable command ID, so they survive commands being added or reordered.
    - A command can have a key-release action (Enter on a Gate clip).
    - `SessionCommands` registers every debug-UI action: transport, edit, file, create and Session. Dialogs come from the window (`ShellActions`).
    - The default shortcuts follow Live and leave the computer keyboard's letters alone. A test checks this.
    - Until 4b the commands act on the debug Session view's selection.
  - **Engine state feed** (`src/ui/feed/`):
    - It ticks on the window's display refresh (`VBlankAttachment`).
    - Listeners are told by aspect: transport, slots, meters, notes, load. Peaks are taken once per tick.
    - The load is read every 0.25 s.
  - **Job pool** (`src/core/JobPool`):
    - It's in `lattice_core`, so the library index and sample loading can use it too.
    - It runs on half the CPU's cores at normal priority.
    - Jobs report progress and can be cancelled; `done` runs on the message thread.
  - **Shell** (`src/ui/shell/`):
    - The layout is as planned. The browser, detail view and info view toggle with Ctrl+Alt+B, L and I, and the choice is remembered.
    - Session, browser and detail are placeholders saying which phase fills them. The Debug UI tab, shown first, holds the whole M2/M3 UI.
    - Keys reach the commands first (the registry's key mappings on the shell), then the computer keyboard.
    - A menu bar is built from the command registry (one menu per category), so every command is reachable before 4g's menus and Find.
  - **Control bar:** as planned, except:
    - **Deviation:** there's no separate overdub button. Session record overdubs into playing clips, as it did in M2.
    - **Deviation:** the "disk" meter waits for the disk work it would measure (4e, 4g).
    - **Deviation:** the per-thread CPU breakdown shows the worker count and the callback's percentiles. A time per worker needs the engine to measure each worker, which is noted for 4h.
    - The audio load meter shows the 99th-percentile callback load and a dropout count, plus UI frame times on hover.
  - **Frame time:**
    - The shell measures the UI thread's work per frame (the feed's ticks plus everything the window paints) against the 8 ms budget, in the audio callback's histogram type.
    - "Reset Load Statistics" starts it over.
    - Idle CPU is measured in 4h, with the views it depends on.
  - **Tests:**
    - `tests/ui/`: ThemeTests, WidgetTests, CommandTests, FeedTests and ShellTests;
    - `tests/core/JobPoolTests.cpp`;
    - `"[.ui-snapshot]"` writes the widget gallery and the shell in every theme to PNGs.

## 4b: Session view and mixer
- **Clip grid:**
  - Clip cells show the name, color, a progress ring while playing, blinking while queued, and a recording state.
  - Empty slots show stop buttons.
  - A scene column shows each scene's name, tempo, and time signature, with launch buttons, plus a master column with Stop All.
- **Editing:**
  - multi-select across tracks and scenes
  - drag to move; Ctrl+drag to copy
  - copy, paste, duplicate (Ctrl+D), delete, rename (Ctrl+R), set color
  - insert scene (Ctrl+I), capture and insert scene, duplicate scene
  - drag a MIDI file in from the OS file explorer to create clips
- **Group tracks** (new in M4, with a small engine addition):
  - A group track is a summing bus with its own device chain and mixer, and groups can sit inside groups.
  - **Engine:** the group becomes a node in M3's routing graph, so delay compensation and the parallel-processing levels include it automatically.
  - **Model:** a `GroupTrack` node with child tracks. Its clip slots launch all the clips in that row for its child tracks, as in Live.
  - **UI:** group headers fold and unfold.
- **Mixer section inside the Session view.** Each part can be shown or hidden:
  - **I/O:** MIDI input from any device or channel; monitoring set to In, Auto, or Off; output routing.
  - **Sends**, with return tracks shown at the right edge and a pre/post setting.
  - **Main strip:** volume fader with meter, pan, track on/off, solo, arm, and a numeric dB box.
  - **Sidechain:** each device's sidechain choice is shown in its device panel. The mixer shows a small routing badge on tracks that feed a sidechain.
- **Track header:** name, color, tuning badge (shows the current tuning; click to change it), and a fold button.
- **Navigation:**
  - arrow keys to move the selection, Enter to launch
  - follow the playing clips (optional)
  - zoom the track width and the scene height
- **As built (2026-10-21):**
  - **Group tracks:**
    - **Deviation (model):** there's no nested `GroupTrack` node. A group is a TRACK of kind "group" (no instrument, no clips), and its members carry its ID and follow it in the flat track list, so a group and everything in it is one contiguous block, and groups nest. This keeps every index-based operation, the undo history and the saved format as they were.
    - **Editing:** grouping takes whole blocks at one level (Ctrl+G), and ungrouping (Ctrl+Shift+G) moves the members up a level. Adding or moving a track joins the group it lands in. Moving, deleting and duplicating a group take its members with it. A group can't be armed.
    - **Engine:** members render first; their faders mix into their group's input; then the groups render level by level, deepest first, each into its parent. A set without groups mixes exactly as before.
    - **Delay compensation:** it lines up every path, including the groups' chains' latency. A member's sends wait for that latency, so they reach the returns in time with the direct path.
    - **Mute and solo:** a muted group silences everything in it. A soloed track keeps its groups audible, and a soloed group everything in it.
    - **Deviation:** a group's fader pans as a balance (unity at the centre), so grouping alone changes nothing you hear. MIDI tracks keep constant-power panning.
    - **Chains and launching:** a group's chain is audio effects only, and groups aren't sidechain sources. A group's slot launches its row and stops tracks with an empty slot there; its slot shows the liveliest state of its row.
  - **Session view** (`src/ui/session/`; the Session tab, shown first):
    - **Clips and scenes:**
      - track headers with a fold button on groups, indentation inside groups, and a tuning badge on MIDI tracks (click to change);
      - clip slots in Live's manner: the launch button launches (a Gate clip until released) and stops; an empty slot shows its stop button, or its record button on an armed track; playing clips show progress round their button, queued ones blink, recording ones are red;
      - the scene column (name, tempo, time signature, launch), the stop row, Stop All, and right-click menus with the commands and a Colour submenu.
    - **Selection and editing:**
      - Shift+click selects a range of slots, tracks or scenes. Delete, Duplicate, Copy, Cut, Paste, Group and Colour work on ranges.
      - Dragging clips moves them, keeping their IDs; Ctrl+drag copies them.
      - Capture and Insert Scene is Ctrl+Shift+I. A MIDI file dropped from the file explorer becomes a clip at the slot it lands on.
    - **Zoom:** Ctrl+wheel sets the track width, Ctrl+Shift+wheel the scene height.
    - **Drawing:** it repaints only what the state feed says changed, plus progress and blinking. Only a change to the set's structure rebuilds the layout and strips.
    - The layout (`SessionLayout`) is plain arithmetic, tested without drawing.
  - **Mixer** (in the Session view, pinned at the bottom):
    - **Strips:** a strip under every column, and the master's under the scene column. It scrolls sideways with the tracks but never out of view (M3 finding 1).
    - **I/O:** a MIDI track's input, channel and monitoring (In, Auto, Off).
    - **Sends:** labelled with the return's letter and showing their level in dB (finding 3).
    - **Main section:**
      - pan, and the fader with its meter and a dB box;
      - the activator (showing the track number), solo, and arm (ringed while auto-armed);
      - "Pre" on returns, and "SC" on tracks that feed a sidechain.
    - **Showing and hiding:** the mixer, its I/O and its sends hide with Ctrl+Alt+M, I and S. The info view moved to Shift+? (Live's) to free Ctrl+Alt+I.
    - **Deviation:** the meters show peaks only (the solid bar too) until the engine reports RMS.
  - **Live input per track** (engine):
    - Monitoring In plays a track's live MIDI always, Auto while armed, Off never (an armed track still records).
    - A track takes MIDI from every input, the computer keyboard, or one input, on every channel or one. Each live message carries its source number, so the audio thread filters without locks.
    - **Deviation:** output routing stays implicit (a track goes to its group or the master); routing to other tracks comes with audio tracks.
  - **M3 hands-on findings:**
    - **2, auto-arm:** on by default (Session menu). The selected MIDI track counts as armed while nothing is armed by hand. It isn't in the document, so it makes no undo step and doesn't mark the set unsaved.
    - **5, the computer keyboard follows a Drum Rack:** on its track, A plays the first pad on show; leaving the track puts the range back.
    - **7, returns:** an effect inserted on a return starts at 100% Dry/Wet.
    - **Still to come:** 4 (inserting where you're looking) and 6 (the Sampler's root) belong to the Device view (4d).
  - **Not done:**
    - "follow the playing clips" (optional);
    - zoom commands (the mouse does it);
    - removing the debug session grid, since the Debug UI tab still holds the device editor until 4d.
  - **Tests:**
    - **Model:** grouping rules, moves, deletes, duplicates, undo, save and load; overlapping clip moves; range duplicates.
    - **Engine:** a group's chain and fader; nesting; mute and solo; compensation (the sends test fails without the send delay); identical output with 0, 1 and 3 workers; group slots; live input by monitoring, input and channel; auto-arm.
    - **UI:** layout and hits; launch and Gate release; double-click, fold and Stop All; scrolling; the mixer's strips and controls; the mixer in view with 64 scenes; I/O; meters; Shift+click, drag move and copy; colours; MIDI drop; the tuning badge; the keyboard following a Drum Rack; auto-arm in the shell; a Reverb on a return fully wet; snapshots.

## 4c: Clip view and piano roll
- **Clip properties panel:**
  - name, color, time signature
  - start, end, and loop markers, with a loop on/off switch
  - launch mode, quantization, legato, and follow actions (A/B, chance, time)
- **Piano roll (MIDI note editor):**
  - **Drawing and editing notes:** a draw mode (B), click to add a note, and drag to move or resize.
  - **Changing selected notes:**
    - Alt+drag duplicates.
    - Arrow keys move notes along the grid or by one table step. Shift+arrow resizes.
    - Selected notes can be split and joined.
  - **Selection:** marquee select, select all, and selecting all notes on one row.
  - **Grid:** adaptive or fixed values, triplets, Ctrl+1–4 shortcuts as in Live, and a snap toggle.
  - **Velocity lane:** draw velocities, ramp across a selection, and edit multiple notes at once. This lane design will later hold MPE, probability, and automation lanes.
  - **Note tools:**
    - quantize (with amount and grid)
    - transpose by **table steps** or by semitones
    - legato, reverse, and invert
    - double or halve the loop, and duplicate the loop
    - stretch time ×2 / ÷2
  - **View:** fold the view to only the notes in use, set the row height, and zoom in both directions, smoothly (cached note layer).
  - **Audition:** clicking a note or a key plays it through the track instrument, using the track tuning. The playhead follows during playback.
- **Colundi-aware note ruler:** the keyboard ruler follows the track's tuning.
  - **12-TET:** note names (C3…), with black and white keys.
  - **Colundi and other table tunings:**
    - Each row shows the index, Hz, and label (e.g. `47 · 440.0`), with no black/white keys implied.
    - **Anchor rows** (exact multiples of 30 Hz) are highlighted.
    - Hovering a row shows its cents and ratio relative to the base frequency.
    - Rows above the playable range (muted under the M1 high-frequency rule) are shaded and marked.
  - **Highlighting:** you can mark a set of table indices to highlight. They're stored per clip or per track. This works like Live's scale highlighting, but for any tuning.
  - **Row height spacing:** an option sets row heights in proportion to the log of the frequency, so the space between rows shows the real interval size in Colundi.

## 4d: Device view and device panels
- **Device chain:**
  - Devices sit in a horizontal row and can be dragged to reorder.
  - Each device has an on/off switch and can be collapsed or expanded.
  - Hot-swap mode (swap a device or preset from the browser).
  - Drag and drop from the browser, with "Save preset" and "Rename" in each device's title bar.
- **Custom panels** (built on the same `ParameterSpec`s; the M3 generic editor stays available as "Show all parameters"):
  - **Synth:** oscillator waveform previews, a filter response curve, envelope graphs you can edit by dragging, and a mod-matrix grid.
  - **Sampler:**
    - a waveform with start, end, and loop markers and slice markers you can drag
    - zoom and scroll
    - a field for the root frequency in Hz, with the matching 12-TET note shown
    - an interpolation-quality switch
  - **Drum Rack:**
    - a pad grid whose page size can be set (4×4 by default; grows with the space available)
    - per-pad choke, tune, and mute/solo settings, and a chain list
    - drop samples onto pads, and drag a pad to move or swap it
  - **EQ Eight:** an interactive curve with draggable band handles and a real-time spectrum analyzer behind it (from M3's FIFO).
  - **Compressor:** a transfer curve, gain-reduction meter, and sidechain source picker.
  - **Reverb:** a visual of the decay time for each of the 3 bands, early/late controls, and the quality mode.
  - **Delay**, **Auto Filter**, **Saturator** (with a curve display), **Chorus**, **Utility**, and **Limiter** (gain-reduction history).
  - **Arpeggiator** and **Chord:** the Chord panel shows the resulting notes as table indices with their Hz on the current tuning.
- **Racks:**
  - **Macro section:** shows any number of macros (0–64) in rows that wrap to fit. A field sets the count. Macro names and colors can be edited, and a variations panel stores and recalls snapshots.
  - **Chain list:** volume, pan, mute, and solo per chain.
  - **Zone editor:** key and velocity zones drawn as bars you can drag, with fade handles.
  - **Map mode:** click a macro, then click any parameter inside the rack to map it. Each mapping's min and max are edited inline.

## 4e: Browser and library
- **Categories:**
  - Instruments, Audio Effects, MIDI Effects, Drums
  - Samples, Presets, **Tunings**
  - Places (user folders you add), Collections (color tags and favorites, as in Live)
- **Library index:**
  - It runs in the background with an **SQLite** database (built in through the amalgamation source).
  - It holds file metadata, tags, and the sample length, channels, and sample rate.
  - The search box searches everything as you type, on any field.
  - Folders are rescanned when they change (file-system watcher through `platform::FileWatcher`: `ReadDirectoryChangesW` on Windows, inotify on Linux), so new files appear without a restart.
- **Preview:**
  - Selecting a sample plays it through a separate preview bus (optionally synced to tempo), and the browser shows its waveform overview.
  - Selecting an instrument preset plays a short sample phrase.
- **Drag targets:**
  - onto a track (insert)
  - onto a device (hot-swap)
  - onto a Sampler or Drum pad
  - a tuning file onto a track header (sets that track's tuning)

## 4f: Tuning tools
- **Tuning picker** in the track header and in the mixer I/O section, with the high-frequency policy shown and editable.
- **Tuning inspector:**
  - A table of all 128 entries: index, Hz, cents from the base, ratio to the base, label, and whether the entry can be played at the current sample rate.
  - Clicking a row plays that note. You can sort the table, filter it, and copy it.
- **Tuning editor:**
  - **Making a tuning:** duplicate any tuning to make a user copy. In the copy you can:
    - edit Hz values and labels
    - shift by an index offset
    - multiply the frequencies by a ratio
    - make a subset (e.g. only the anchor notes, or chosen indices spread across the keys)
  - **Checks:** frequencies must increase, and entries above Nyquist trigger a warning.
  - **Saving:** saves to the user Tunings folder in the Colundi `.txt` format, which M1's parser reads. Scala/TUN export is added in M6.
- **Pitch-bend settings for each track** (Cents or Table Steps, plus the bend range), shown next to the tuning picker.

## 4g: Files, preferences, mapping, and help
- **Files:**
  - New, Open, Save, Save As, and recent sets. A prompt appears when there are unsaved changes, and the unsaved state shows in the title bar.
  - **Autosave and crash recovery:** every 2 minutes, a recovery copy is written in the background. After a crash, the next launch offers to restore it.
  - **Collect All and Save:** copies the samples a set uses into the set's folder.
  - **Missing files dialog:** searches the library index for moved samples.
  - **Undo history panel**, which lets you jump to any earlier point.
- **Preferences** (tabs):
  - **Audio:** device, sample rate, buffer size, the measured input and output latency, a test tone.
  - **MIDI:** which ports are enabled for tracks, clock sync, and remote control.
  - **Controllers:** a placeholder until M5.
  - **Look & Feel:** theme, zoom, colors.
  - **Library:** folders and rescanning.
  - **CPU:** multi-threading on/off and the worker count.
  - **Tuning:** the default tuning for new tracks and the default high-frequency policy.
  - **Computer keyboard:** keys and the range step per tuning.
  - **Shortcuts:** a full editor with conflict detection and import/export.
- **MIDI Map mode (Ctrl+M):**
  - Map any parameter, clip slot, scene, or command to a MIDI note or CC from any MIDI device.
  - Options: min/max range, takeover mode (Pickup or Value Scaling), and relative or absolute encoders.
  - Mappings are saved in the set.
  - This lets any MIDI controller be used even before M5 adds dedicated drivers.
- **Key Map mode (Ctrl+K):** the same, but mapped to computer keys. It respects the computer keyboard's note keys when that keyboard is on.
- **Find (Ctrl+F):** one search box, as in a web browser, for everything you can reach. It makes every control, setting and feature easy to find without hardware.
  - **What it finds:**
    - **controls in the set:** every device parameter, mixer control and clip setting, by name or by group (e.g. "release" finds every envelope release, the Compressor's and the Limiter's);
    - **settings:** the Preferences entries;
    - **commands:** every command, with its shortcut.
  - **Results show where each one lives**, e.g. "Synth › Amp Env › Release · 2 MIDI".
    - The ones on the selected track come first, then other tracks, then settings, then commands.
    - Matching is as you type, on whole words and on word starts ("amp rel").
  - **Choosing a result takes you there:**
    - it selects the track;
    - it opens the device in the Device view, expanding it and opening the rack chain if needed;
    - it scrolls the control into view and briefly highlights it.
    - A parameter that the custom panel doesn't show opens in "Show all parameters". A setting opens its Preferences tab. A command runs.
  - **Ctrl+Shift+P** opens the same box filtered to commands (a command palette).
  - **Shortcuts:** the browser's search field is Ctrl+Alt+F, since Ctrl+F is taken by Find.
  - Typing a value into the search ("cutoff 800") is not planned; it's added later if it proves useful.

## 4h: Quality pass
- Accessibility check: keyboard navigation through every view, and screen-reader labels.
- Performance profiling against the targets. The UI benchmarks below go into the same baseline system as M3's benchmarks.
- Visual consistency check across themes at 100%, 150%, and 200% zoom.
- Delete the M2/M3 debug UI, keeping the generic device editor as "Show all parameters".

## Tests
1. **Logic for each view**, tested without drawing anything:
   - piano-roll edit operations (draw, move, resize, split, join, quantize, transpose in table steps, legato, reverse, invert, stretch)
   - grid and snap math, including triplets and adaptive grids
   - zoom and scroll conversions
   - the session grid's selection and copy/paste/duplicate
   - fitting macros into rows
   - zone-editor handle math
2. **Find:**
   - Every parameter of every device type can be found by its name and by its group, for a device on a track, on a return, on the master and inside a rack chain.
   - Choosing a result makes its control visible and highlighted (checked headless: the control is showing and within the view's bounds).
   - Results come in the stated order, and a search over a 32-track set with 64-macro racks answers within one frame.
3. **Command coverage:**
   - A test lists every engine command and model operation and fails if any of them has no registered UI command. This enforces the no-hardware rule.
   - The shortcut table must have no conflicts by default.
4. **Undo fuzzing:** 10,000 random UI operations (using the same commands the UI uses), then undo them all. The model must match the starting model exactly. Then redo them all, and the model must match the end state.
5. **Render snapshot tests:**
   - Key components are drawn into images without opening a window: the session grid, the Colundi piano-roll ruler, the EQ curve, the Drum Rack pads, and the macro section.
   - Each is drawn in every theme at 100% and 200% zoom and compared against reference images, with a tolerance.
6. **Colundi ruler:**
   - The labels match the table.
   - Anchor rows are exactly the multiples of 30 Hz.
   - With log-spaced rows, the space between rows is proportional to log(f).
   - Rows above Nyquist are marked as unplayable.
7. **Library:** indexing a fixed test folder gives the expected records. Search ranking is checked on fixed queries. The watcher notices added, removed, and renamed files.
8. **Files:**
   - Autosave followed by a simulated crash recovers the set.
   - Collect All and Save copies every file the set uses, and the set reopens from its new location.
   - The missing-file finder relinks a moved sample.
9. **MIDI and Key Map:** each mapping type round-trips through a save. Pickup takeover doesn't jump. Relative encoders step correctly.
10. **UI performance (enforced, as in M3):**
   - Paint time for the 32×16 session grid with meters moving.
   - The piano roll with 10,000 notes while zooming and scrolling.
   - A Device view showing a rack with 64 macros.
   - The browser filling 100,000 search results.
11. **Audio is unaffected by the UI:** an automated UI stress script (fast scrolling, zooming, dragging, opening many views) runs against a live engine at a 64-sample buffer for 10 minutes. It must cause **zero dropouts** on the reference machine.
12. **Edits reach the engine:** the view-logic tests in item 1, and the session and device panel
    commands, also run against an engine rendering through `OfflineRenderer`. After each edit, the
    rendered output changes as the edit says (a device inserted is heard, a send turned up reaches
    its return, a sidechain source chosen ducks). Edits made while rendering are included, not
    only edits made before the first block (M3 hands-on finding).

## Definition of done
- [ ] The debug UI is gone, and every M2/M3 feature is reachable from the new UI, from the menus, and from Find (Ctrl+F), which also finds every control and setting.
- [ ] You can build a full session with no controller connected: groups, returns, sidechain, racks with 16+ macros, and a Drum Rack. Clips are recorded and edited in the piano roll on a Colundi track, and the set is saved, reopened, and recovered after a forced crash.
- [ ] The piano roll on a Colundi track shows the index, Hz, and anchor highlights, and editing in table steps works.
- [ ] A user tuning made in the tuning editor can be saved, used, and reloaded.
- [ ] Every frame-time target is met. The UI stress test causes zero dropouts at a 64-sample buffer.
- [ ] Themes and zoom levels from 50% to 250% look right on every snapshot-tested component.
- [ ] All tests pass in CI. Benchmarks are within budget on the reference machine.
- [ ] The M3 hands-on findings ("Starting point") are resolved, each checked hands-on.
